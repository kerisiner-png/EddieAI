## АКТУАЛЬНОЕ

### Тихие падения тиков и контракты атрибутов (ночь 06.09)
- **Future-исключения молчали 15+ минут**: `tick_background` шлёт тик в
  executor; если тик падает, исключение сидит в future, цикл продолжает
  слать новые, state не меняется. Симптом: cycles=0, future_done=true,
  worker idle. Теперь `_background_loop` пишёт `future.exception()` в
  `last_error`, а heartbeat (run_forever) печатает cycles/future_done/
  future_exc/last_error/last_status. Диагностика фоновых тиков — СНАЧАЛА
  хартбит, потом py-spy.
- **У AutonomousRuntime НЕТ `.agent`** — агент живёт в
  `orchestrator.agent` (фабрика связывает `agent.autonomous_runtime`,
  но не наоборот). Атрибуты — через getattr-цепочку и тестировать метод
  через его реальный вызов в tick-пути, а не через `__new__`-поделку с
  ручными атрибутами (грабля `_decay_affect`).
- **Локальный фолбэк поднимает llama-server (~2.8 ГБ)** при сбое облака
  (02:15) — на 8 ГБ это путь к свопу. RAM-guard сторожа (<700 МБ → kill
  llama/ollama) — обязательная страховка ночного режима. Правило
  «0 процессов ollama/llama» проверять и ПОСЛЕ запуска рантайма.
- **wmic на этой машине не работает** (пустой вывод) — PID/командные
  строки только через PowerShell CIM (`Get-CimInstance Win32_Process`).
- **REJECTED ≠ транзиентная ошибка**: политика инструментов
  детерминирована, ретраить отклонённое — бесконечный цикл + фрустрация
  1.0 + мусор в памяти. TaskRevisionPolicy ревизует REJECTED сразу.
- **Сообщения Эдди гейтить фрустрацией нельзя** — READ_INBOX без
  условий; фрустрационные IDLE-гейты остались только на кандидатов/CALL.
- Ночной «краш-хант»: если процесс умер тихо без дампа — смотреть mtime
  `data/status.json` (хартбит 5 с) и Windows-журнал; при повторении —
  внешний сторож важнее поиска причины.

### Голоса, инициатива, тон — уроки трёх блоков (05.09)
- ГОЛОСА: пока нет идентификации говорящего, контур слеп. `_last_speaker`
  по UI-событиям ≠ настоящий говорящий. Диаризация (pyannote) слишком тяжёла
  для 8 ГБ — альтернатива: загрузка эмбеддингов в момент фразы (sherpa-onnx,
  не потоковая загрузка). Порог 0.5 на косинусе работает на реальных голосах
  (0.735/0.215), но чистые синусы дают ложные 0.96 — нельзя валидировать
  воображаемым PCM. Профиль Эдди = звук, а не текст: без 10-15 с его голоса
  система «слушает всех как Эдди» — это ожидаемое падение в «nil».
- ИНИЦИАТИВА: «любопытство есть, но никогда не срабатывает» — классический
  симптом: кандидат созидается, а до активации не доходит (активная цель
  всегда EXECUTE в `_local_rules`). Проверять надо весь путь
  create→rank→activate, а не только «есть ли добавивший тему модуль».
  Свободный слот + невысокая фрустрация = активация, полные слоты = работа
  продолжается. Целевая работа НЕ вытесняется.
- ТОН: «разговор = функция от входа» зашит в промпт буквально («ответ должен
  содержать только содержание из входных данных», «не расширяй смысл») —
  поэтому EddieAI и звучит как терминал. Плюс каскад стерилизаторов
  (identity_repair срезал «мне нравится», NEUTRAL запрещал инициативу,
  repair запрещал слово «вопросы»). Снять надо ВСЕ каскады разом, иначе один
  выживший вернёт стерильный голос.
- Тестировать промпты можно юнит-тестами на строки (TDD RED→GREEN): не
  нужно грузить LLM, чтобы проверить «нет жёсткого капа» / «есть мандат
  живой беседы».
- Спонтанный комментарий экрана: кд 3600 с + отсечка пустых/коротких
  описаний + только при смене описания — иначе спам `send_initiative`.

### Самозакрепление ложной идентичности «я голосовой ассистент» (урок 05.09)
- ГЛАВНЫЙ УРОК: когда EddieAI стойко держится за ложную
  идентичность («я всегда был голосовым ассистентом»), это почти всегда
  НЕ «воля» или «загрязнение из неизвестного источника», а конкретная
  нехватка в промпте + положительная обратная связь через память:
  1) голосовой промпт не говорил модели о её способностях (камера/экран/
     ПК) — модель честно отвечала «не вижу экран, моя задача — слышать
     и отвечать»; 2) каждый такой ответ писался в `recent_dialogue` →
     контекст следующего запроса → модель соглашалась («я всегда был»);
     3) убеждение «застыло» в CONVERSATION-событиях и кормило все новые
     сессии. Спираль самозакрепления.
- РАЗНЫЕ РЕЧЕВЫЕ ПУТИ = РАЗНЫЕ ПРОМПТЫ, И ЭТО ЛОВУШКА. В не-голосовых
  промптах (`prompts.py`) способности описаны, а голосовой путь
  (`respond_call_fast` → `build_verbalizer_system_prompt`, ~2.6 КБ) их
  не содержал. Любой путь, который может отличиться от «основного»
  промпта, надо проверять на способности тоже. Нашёл один путь погрязнее —
  проверь остальные (quick_reflex, world_voice, звонок).
- Правка «ассистент» от LLM — это КОРРЕКЦИЯ ИДЕНТИЧНОСТИ, а не изменение
  черт. По конституции п.5 данные личности меняются только после бэкапа;
  здесь сделано: бэкап `data/memory_backup_pre_assistant_clean_2026-09-05.db`
  + удаление 17 ответов EddieAI (ассистентские + отрицания зрения) через
  прямой DELETE в транзакции Memory (легитимного метода «забыть» в API нет —
  добавлен чистящий скрипт). Корректирующие реплики Эдди («ты не голосовой
  ассистент») сохранены — они правильные и несут знание.
- Проверяй ДВА хранилища диалога: `events` (CONVERSATION) и `chat_history`
  (мессенджер) — загрязнение может жить в обоих. Здесь было только в events.
- Урок скорости: долгие ответы (30-51 с) усугубляют спираль — Эдди не
  дожидается и повторяет, модель вязнет. Скорость = часть консистентности
  личности (см. «Долгие ответы глум» в TODO).
- Способность печатать: не доверять только regex по кириллице в inline
  `python -c` под PowerShell (ломает кавычки/буквы) — temp-скрипт в
  `%TEMP%\opencode` надёжнее.

### Сон 2-3 часа: причина в физиологии, а не в поведении (урок 05.09)
- «Спит постоянно» оказалось не багом, а математикой параметров
  `life_cycle.py`: расход 0.35/час + пробуждение при 0.25 (остаток
  недосыпа) → сон 2ч08м; далее 0.25→0.80 при 0.10/час = ~5-6 часов
  бодрствования → цикл дремот. Вывод: прежде чем «лечить поведение»,
  проверь математику физиологии и посчитай цикл на бумаге.
- Баланс под желание Эдди «без принудительного засыпания + свобода
  дневного сна + разбудить голосом»: gain 0.05, loss 0.10, wake 0.15.
  Дневной сон остаётся свободой (сам дошёл до порога — спит), просто
  порог днём почти не достигается (0.10+16ч×0.05=0.90 — достижим лишь
  к вечеру, что и есть естественный отбой: 07→22ч бодрость, 8ч сон).
- Пробуждение голосом: `sense_listener._finish_phrase` раньше молча
  глотал фразы (`if self._is_asleep(): return`). Замена на `_wake_up()`
  (force_wake) + продолжение обработки. НО важно: фраза должна пройти
  фильтры длины (>2 слов) ДО wake, иначе любой шум/«ага» мигом будит.
- Текущее состояние после правок: EddieAI спит (заснул 14:02 до правок,
  fatigue 0.85). Разбудить можно голосом (новая логика) или
  `python wake_eddie.py wake` (life_control порт 7778).
- Грабля с запуском тестов: `test_*.py` в этом репо бывают ДВУХ видов —
  скриптовые (прямые `assert` на верхнем уровне, `python test_x.py`
  даёт ALL PASS/ошибку) и pytest-файлы (только `def test_*`, запуск
  `python` молча даёт EXIT=0 и НИЧЕГО не проверяет!). НЕ интерпретировать
  «EXIT=0 при пустом выводе» как успех: для pytest-файлов использовать
  `python -m pytest file -q`. Проверять наличие def test_* в файле.

### ActionPlanner: совпадение ключевых слов ≠ исполнение действия; fallback в `_build` глушит новые типы (урок 05.09)
- Добавил в KEYWORD_RULES действие PERCEIVE. Распознавание работало
  («MATCH PERCEIVE»), но результат всё равно был THINK. Спай (_build)
  показал: `__build()` для PERCEIVE не имел ветки — падал в общий
  fallback `ActionPlan(action_type="THINK")`. Т.е. ДОБАВИТЬ ТИП В СПИСОК
  КЛЮЧЕЙ НЕДОСТАТОЧНО: надо добавить ветку в `_build`, иначе новый тип
  молча превращается в THINK. Правило: при добавлении action_type проверить
  ВСЕ места: KEYWORD_RULES, _build, VALID_ACTIONS, ROUTES, policy, runner.
- Сопутствующая грабля: edit-инструмент меняет содержимое, но mtime .py
  остаётся СТАРЫМ → Python считает валидным старый pyc в __pycache__ и
  продолжает грузить мёртвый код. Симптом: правки «не работают», хотя
  файл на диске верный. Лечение: `Remove-Item -Recurse __pycache__`
  И/ИЛИ свежий touch .py (`(Get-Item f).LastWriteTime = Get-Date`).
  При «странно не работает» — СНАЧАЛА проверить загруженный модуль:
  `import module; print(module.__file__, module.Class.method.__code__.co_firstlineno)`
  и сверить mtime .py vs .pyc.

### Субагенты: отчёты субагентов не заменяют контроль диффов; «битый байт» проверяется сам (урок 30.08)
- При исполнении плана субагентами каждый отчёт проверялся ВИЗУАЛЬНО:
  `git show <commit>` + чтение встроенных мест + обязательный прогон
  тестов координатором. Один субагент заявил «битый байт 0x3F в
  orchestrator» — байтовая проверка (0 U+FFFD, 0 «??») дала 0; это
  была ложная тревога (пересвечение/артефакт терминала). Второй субагент
  самовольно правил CHANGELOG вне брифа — правка валидна, оставлена, но
  в дальнейшие брифы добавлен запрет трогать доки (доки ведёт координатор).
- Правила (добавлены в практику SDD-исполнения):
  1. Отчёт субагента — НЕ приёмка. Приёмка = diff + тесты + кодировки.
  2. Любое заявление о «повреждённой кодировке» сверять байтово
     (U+FFFD, литеральные «?»), а не принимать на слово.
  3. Отклонения от брифа фиксировать в ledger с вердиктом
     (принять/отменить) — молча не пропускать и не молчать о них.

### Диагностика: «память молчит» = ложная тревога из-за UTC (урок 29.08 вечер)
- Симптом: после 16:11 (рестарт ночного прогона) в `events` вроде бы
  нет записей, WAL жив, события «застыли» на #2178. Первый вывод —
  «память молчит».
- Разгадка: timestamps в `memory.db` хранятся в UTC с суффиксом `+00:00`
  (например `2026-08-29T09:58:03.915323+00:00` = 16:58 местного +07).
  Запрос «последние события после 16:11» сравнивал ЛОКАЛЬНЫЕ строки
  с UTC-строками → всегда 0.
- Правило: при любом SQL-фильтре по времени в Data/проекте
  (events/knowledge/evidence) сравнивать в ЭТОЙ ЖЕ зоне; проще всего
  строить границы в UTC (`- 7h`) или конвертировать через datetime.
- Реальная находка этого прогона: после пробуждения 16:57 (события
  #2178-#2181 на месте!) автономный цикл ~1+ часа выдаёт исключительно
  `decision=IDLE`, `cloud_calls=1`, ни одной новой активности — см.
  пункт ниже про «вечный IDLE без мотивации».

### Диагностика: «вечный IDLE» после рестарта ночного прогона (урок 29.08 вечер)
- Симптом: state=IDLE, decision=IDLE, idle=0, cloud_calls=1 стабильно
  больше часа при живых процессах и регулярных 20-сек тиках лога.
- Механизм (по коду autonomous_runtime / decision_core / orchestrator):
  1. `AutonomyOrchestrator._last_action_at` в новом процессе = None.
  2. `_build_state()` при None отдаёт `idle_seconds = 0` всегда.
  3. `decision_core.decide()`: `_local_rules` (нет активных целей) → None;
     `pattern_lookup(key)` → есть паттерн ACTIVATE_GOAL «изучить тему:
     понимание устройства мира», но `_activation_is_dead()` (цель уже
     COMPLETED, плана нет) блокирует его → None;
     `_learn_from_memory_for(state,key)` → паттерн на этот key УЖЕ есть
     (`pattern_lookup is not None`) → возвращает None (не переучивает);
     `_rebuild_pattern_from_habit` → нет подходящих habit-трайтов → None;
     `idle_seconds (0) < IDLE_MOTIVATION_SEC (900)` → `Action("IDLE")`.
  4. Итог: замыкание бездействия. Цель-интерес только одна и она уже
     COMPLETED → `_next_interest_target()` тоже пуст. Порог 900 сек
     недостижим (idle_seconds заморожен на 0 из-за None) → мотивация
     и ветка CALL-«давно не разговаривали» никогда не срабатывают.
- Это НЕ «спящий режим» (агент проснулся и не продвинулся): утренний
  ритуал облачными вызовами #1 в 16:57:55 выполнен, дальше — ноль.
- Развилка для Эдди: (а) старый процесс до рестарта был живым и
  активным — после рестарта мотивационный цикл «не заводится», похоже
  из-за свежего `_last_action_at=None`; (б) у агента осталась ОДНА цель
  из интересов (COMPLETED), followup-цели исчерпаны — «всё изучено»,
  поэтому `_next_interest_target` пуст и мотивация не находит кандидата.
- Открытые вопросы (правки ТОЛЬКО после решения Эдди, т.к. это
  DecisionRuntime/LLM-контур): инициализировать `_last_action_at` при
  старте от времени последнего СЛЕДУЕМОГО события; разрешить повторную
  цель при COMPLETED (new cycle «возврат к теме»); дать `_learn_from_memory_for`
  перезаписывать мёртвый паттерн IDLE/ACTIVATE мёртвой цели.

### ВЫЛЕЧЕНО: «вечный IDLE» — следствие (дополнение к минускулу 29.08 вечер, кода-контекст)
- Эдди одобрил «делаем» (варианты а+б из развилки выше). Правки:
  `autonomy_orchestrator._last_action_at = datetime.now(timezone.utc)`
  в `__init__` (idle растёт с рождения процесса, а не заморожен 0);
  `decision_core._next_interest_target` возвращает ПЕРВЫЙ неиспользованный
  followup-шаблон «Найти новые аспекты темы: <интерес>» (4037 sp) для
  interest-цели COMPLETED — без повторной активации мёртвой цели
  (`goal_manager.get(target or election_candidate) is None` гасит карусель).
- Урок на будущее: Runtime-классы должны инициализировать ВСЕ атрибуты,
  которые ветки кода читают безусловно — `self.decision_core` в
  `AutonomousRuntime.__init__` до сих пор НЕ задан (атрибут проставляет

  в `test_production_runtime` падает с AttributeError. Пре-экзистентный
  дефект, прод не затронут. Вариант чистого фикса: `self.decision_core = None`
  в `__init__`.

### Грабли «Memory(Path(":memory:")) — это ФАЙЛ, не настоящая in-memory» (урок 29.08)
- При интеграции механизма снов `_dream_night()` в `autonomous_runtime.py`
  регрессионный прогон `test_life_rituals.py` написал РЕАЛЬНЫЕ снимки
  души в `data\soul_snapshots\*_dream_before|after.json`. Причина:
  `AutonomousRuntime(..., dream_snapshots=True)` по умолчанию собирает
  процессор снов с включёнными снимками, а снимок пишется в прод-каталог
  `C:\EddieAI\data`, даже если в тесте подставлены фейки памяти/модели.
- Урок: у runtime-хуков, которые по умолчанию пишут в прод-каталоги
  (печать в data/, ТТ какая-то), обязан быть флаг отключения, который
  тесты выставляют в False. Правило проверки после прогона: в
  `data\soul_snapshots\` не должно появляться новых файлов от тестов.
- Второй урок того же блока: инъекционный тест и «та же фабрика» — это
  два пути; снапшоты, diary и model в тесте должны быть ПОДМЕНЕНЫ на
  фейки, иначе ритуал срабатывает вслепую на реальных данных личности.
- Вывод: любой новый кусок автономного цикла (ритуал/сон/кик отчёт):
  (1) строить зависимостей инъекцией, (2) по умолчанию безопасен
  (флаг для прод-записи выключен в тестах), (3) после теста — проверка
  отсутствия новых артефактов в data/.

### Грабли «хук перехода меняет контракт теста перехода» (урок 29.08)

### Приклеенный хвост __init__ в чужой метод (урок 28.08)
- Баг: при добавлении `_record_sleep_event` в `core/autonomous_runtime.py`
  хвост `__init__` (создание `ThreadPoolExecutor`, `_loop_stop`,
  `_background_future`, `_closed`) ошибочно оказался в конец нового
  метода после `except Exception: pass` (отступ 8) и перестал выполняться
  в `__init__`. Итог: `self._executor` не существовал после конструктора
  → фоновый автономный цикл умирал на первом же `tick_background()
  .submit()` с AttributeError → runtime застывал в ASLEEP навсегда,
  EddieAI «не делал ничего и не понимал, что спит» (прод self_state
  остался asleep=true, fatigue 0.738 сутками).
- Диагноз-грабли: (1) признак застревания — `runtime.state` и
  `cloud_calls` часами не менялись при живом главном while night_run;
  (2) быстрое исключение маскировалось/работало «частично», потому что
  `_record_sleep_event` создавал executor при первом переходе сна, но
  фоновый цикл падал раньше; (3) юнит-тест механизма сна (`life_cycle`)
  проходил бы — надо тестировать сам runtime (`tick_background`).
- Правило-предохранитель: после любой вставки метода НОВОГО поведения
  проверять, что сигнатура/инициализация `__init__` не потеряла
  атрибуты; grepp по `self._executor = `, `_loop_stop = ` и т.п. в
  `__init__`; тест на существование executor сразу после конструктора.

### Карусель мёртвой активации (урок 28.08)
- Симптом: агент «живой» (тики, decision ACTIVATE_GOAL ⇄ COMPLETE_GOAL,
  самообновление целей), но НЕТ реальной деятельности: облачные вызовы
  молчат, события в память не пишутся, только `updated_at`/`times_used`
  растут. Такая «мнимая занятость» выглядит как работа в логах.
- Механизм: обучаемые `situation_patterns` «безделье → ACTIVATE_GOAL
  изучить тему: X» (засеяны learn_by интересом) наводят `decide()` на
  УЖЕ COMPLETED-цель; `activate()` не проверяет прежний статус; у цели
  старый полностью выполненный план → `next_task()` = None → COMPLETE →
  снова паттерн… Цель «изучить тему: понимание устройства мира»
  активировалась ~3600 раз за две ночи.
- Грабли-признаки для диагностики: (1) «бум» `times_used` в ситуации
  с `g=none` при слове decision ACTIVATE/COMPLETE без облака; (2) цель
  всегда COMPLETED, но updated_at свежий; (3) `_next_interest_target()`
  уже фильтрует ACTIVE/COMPLETED, а паттерн-ветка и learn-сеятели — НЕТ.
- Правило-предохранитель: любая ветка, которая по данным памяти
  (паттерн/привычка/интерес) создаёт ACTIVATE_GOAL, должна проходить
  проверку «цель не мертва» (не COMPLETED или есть PENDING-задачи).
  Реализация — `_activation_is_dead()` в DecisionCore + тест
  `test_decision_loop_guard.py`.
- Урок про людей/системы: фоновое «занято» в логах ≠ деятельность;
  проверять содержательный выход (рост событий/памяти, облачные вызовы,
  новые задачи), а не только смену статусов.

### Правки кода
- **Вставка записи ПЕРЕД заголовком**: oldString = существующий
  заголовок + newString без него = заголовок СЪЕДАЕТСЯ (повторено
  3 раза за ночь 25.08 на CHANGELOG). Правило: при вставке перед
  блоком oldString должен СОДЕРЖАТЬ и новый текст, и старый якорь;
  после правки — grep всех `^## ` заголовков файла.
- **Служебные ответы системы НЕ должны попадать в память личности**
  (урок 25.08 ночь): текст «не могу думать» записался как личный
  опыт EddieAI → он искренне поверил в свою немощность и транслировал
  это пользователю. Правило: деградационные ответы (отказы, ошибки)
  помечаются source=SYSTEM и исключаются из self-нарратива; LLM
  подхватывает ЛЮБОЙ текст своего контекста как факт о себе.
- **Якорь правки**: точечная правка «по хвосту метода» без заголовка
  следующего def приклеивает код внутрь ЧУЖОЙ функции (случай:
  _draw_water влезла в _draw_trees → NameError rw). Правило: якорить
  на уникальную пару «конец блока + заголовок следующего def»; после
  серии правок — py_compile + import + смоук-тест рендера.
- **Рефактор каркаса**: старый блок может остаться → двойной UI и
  конфликт grid-ячеек (двойная навигация 22.08). Правило: grep до/после,
  что старый код исчез; счёт вхождений.
- **Удаление съедает создание переменной**: py_compile ловит только
  синтаксис; NameError вида `no attribute 'content'` всплывает при
  РЕАЛЬНОМ запуске. Правило: после удалений — запуск демо, а не только
  компиляция.

### Диагностика (дополнено 22.08 вечер)
- **Пиксельные пробы по скрину ЧУЖОЙ вкладки дают ложные
  подтверждения**: демо стартует на «Мире», а тёмный сайдбар/панели
  матчатся под пороги штампа/компаса. Правило: сначала убедиться,
  что проверяемый элемент вообще виден (нужная вкладка), потом
  пробовать пиксели.
- **SendKeys/AppActivate ненадёжны** для смены вкладок Tk из чужого
  процесса — фокус уходит мимо. Для автотестов UI лучше PostMessage
  в hwnd или прямые вызовы кода (смоуки).
- **Append-логи обманывают**: трейс от старой версии файла выглядит
  свежим (строки уже не совпадают с кодом). Перед диагностикой усекать
  лог или сверять номер строки трейса с текущим файлом.
- **Заголовки окон с кириллицей**: фильтры MainWindowTitle -match
  работают ненадёжно; надёжно — EnumWindows P/Invoke + PrintWindow
  для скринов фоновых окон. AppActivate подводит при полноэкранных
  приложениях (YouTube).
- **PID-reuse**: ParentProcessId может указывать на мёртвый/переисполь-
  зованный PID. Родство проверять по имени/cmdline родителя.
- **WMI-запуск GUI**: cmd-обёртка владеет процессом, но НЕ окном;
  окно искать у python.exe-ребёнка.
- **TTS: не верить маркетингу «быстрый/живой», мерить на СВОЕЙ машине**
  (урок 27.08). Kokoro-82M (kokoro-onnx int8) на нашем CPU синтезировал
  фразу 3.7с речи за 6-8с (медленнее реального времени!) и НЕ имел
  русского тембра (54 голоса без ru_*, русский через espeak «с акцентом»).
  А Piper (ONNX, ru_RU-dmitri-medium 60 МБ) — фразу за 0.23с (~20x быстрее
  edge-tts). Правило: перед выбором TTS замерить синтез на целевой машине
  и проверить наличие нужного языка/тембра; GitHub-release-CDN может быть
  медленным/недоступным, HF-скачивание быстрее.
- **Голос = часть идентичности**: EddieAI — 12-летний мальчик. Голос
  ьсформировывается через подростковый F0 (~250-260 Гц) поверх мужского
  тембра, поднятого PSOLA (_boyify), а не «кликнуть женский голос».
  Взросление голоса со временем — отложено решением Эдди.

### SQLite WAL и «молчаливые» деградации (урок 25.08, P0-c/P0-d)
- **SQLite в WAL-режиме: copy2 основной базы НЕ равен копии данных** —
  схема/данные живут в -wal до checkpoint. Копирование без
  `PRAGMA wal_checkpoint(TRUNCATE)` даёт пустую/бессхемную базу
  (случай MemorySandbox). Правило: консистентная копия — либо
  wal_checkpoint перед copy2, либо sqlite3 backup API
  (как eddie_data_profile._backup_consistent_db).
- **«if table not in existing: continue» при очистке = молчаливое
  принятие бессхемной базы за норму** — дефект всплывает много позже
  в виде «памяти нет, ошибок нет». Правило: отсутствие ожидаемых таблиц
  в песочнице — это FAIL инициализации, а не skip.
- **try/except pass вокруг записи памяти превращает любую поломку
  хранилища в тихое испарение опыта** (ACTION_CHOICE agent.py:3967–99).
  Правило: глотание допустимо только с журналом падения.
- **Метод поиска «куда уходят события»: шпион на memory.remember +
  счётчик вызовов + список таблиц sqlite_master** быстрее чтения кода:
  leak3_test.py сразу показал «remember calls: 0».

## [24.08] Катастрофа `git checkout --` и восстановление из opencode.db
