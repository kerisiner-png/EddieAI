# Аудит ALL — батч 43

Файлы: main.py, database.py, events.py
Модель: deepseek-v4-flash

Мы провели глубокий аудит кода. Ниже представлены найденные проблемы по каждому файлу.

## main.py

1. **Строка 6-9**: Импорт `AutonomyRuntimeFactory` с многострочным синтаксисом, но это не ошибка, просто стиль. Однако импорт `traceback` после импорта из core — нарушение порядка (стандартные библиотеки должны идти первыми). Это LOW.

2. **Строка 13**: `LOG_DIR = r"C:\EddieAI\logs"` — жёстко заданный путь. Это хрупко: на других системах может не быть такого пути, и программа упадёт при создании каталога. Лучше использовать относительный путь или переменную окружения. Серьёзность: MEDIUM.

3. **Строки 16-31**: Класс `Tee` — перехват stdout/stderr. Потенциальная проблема: если файл не может быть открыт (например, нет прав), программа упадёт. Также нет обработки ошибок при записи. Но это не критично. Ещё: `Tee` не закрывает файл (нет метода close), но это не страшно, так как процесс завершится. Однако при длительной работе может быть утечка файловых дескрипторов? Нет, файл один. Но если `Tee` будет создаваться несколько раз, то старые файлы не закрываются. В данном случае создаётся два объекта Tee (для stdout и stderr) с одним и тем же файлом — это нормально, но оба пишут в один файл, что может привести к перемешиванию. Это допустимо.

4. **Строка 48**: `sys.stdout = Tee(...)` — замена sys.stdout на объект Tee. Но `input()` использует sys.stdout и sys.stdin? На самом деле input() использует sys.stdin и sys.stdout для приглашения. При замене stdout на Tee, приглашение будет писаться и в файл, и в консоль — это нормально. Но есть нюанс: `Tee.write` вызывает `self.stream.write(data)` — это оригинальный stdout, который уже сохранён. Всё верно.

5. **Строка 55**: `agent = Agent()` — нет обработки исключений при создании агента. Если инициализация упадёт, программа завершится с traceback, но это не страшно.

6. **Строки 57-60**: Создание runtime через фабрику. Нет проверки на None.

7. **Строки 70-104**: Основной цикл. Есть потенциальная проблема: `input("Эдди > ")` — если пользователь введет EOF (Ctrl+D / Ctrl+Z), возникнет EOFError, который не обрабатывается. Это приведёт к аварийному завершению. Нужно обернуть в try-except EOFError. Серьёзность: MEDIUM.

8. **Строка 73**: `if first.lower() == "exit":` — регистронезависимо, но если пользователь введет "exit " с пробелами, то `.strip()` уже убран, так что ок.

9. **Строки 76-84**: Сбор многострочного ввода. Внутренний цикл `while True: line = input()` — если пользователь введет EOF, снова EOFError. Не обработано.

10. **Строка 86**: `user_message = "\n".join(lines).strip()` — если lines пуст? Но first уже не пустой, так что lines содержит как минимум first. Ок.

11. **Строка 91**: Проверка `len(user_message) < 2` — слишком строго? Может, сообщение из одного символа (например, "?"), но это допустимо. Не ошибка.

12. **Строка 99**: `answer = agent.respond(user_message)` — если respond возвращает None, то print выведет "None". Но это не ошибка.

13. **Строка 102**: `traceback.print_exc()` — печатает traceback в stderr, который теперь Tee, так что попадёт в лог. Ок.

14. **Строка 106**: `finally: agent.close()` — если agent не был создан (исключение при создании), то agent не определён, и будет NameError. Нужно обернуть создание в try или инициализировать agent = None. Серьёзность: HIGH.

## memory/database.py

1. **Строка 1-5**: Импорты: `from pathlib import Path`, `import os`, `import sqlite3`, `import threading`. Всё стандартно.

2. **Строка 8-12**: `_DATA_DIR = Path(os.environ.get("EDDIE_DATA_DIR") or (Path(__file__).resolve().parent.parent / "data"))` — если переменная окружения задана, но путь некорректен, то будет ошибка при создании. Но это не баг.

3. **Строка 15**: `DB_PATH = _DATA_DIR / "memory.db"` — глобальная переменная, используется по умолчанию. Ок.

4. **Строка 18-29**: Декоратор `_synchronized` — использует `self._lock`. Но `_lock` создаётся в `__init__` до вызова `_initialize`, так что всё верно. Однако декоратор не обрабатывает исключения — если метод бросит исключение, блокировка будет снята (контекстный менеджер with). Ок.

5. **Строка 31**: `class Memory:` — нет наследования, ок.

6. **Строка 33**: `def __init__(self, db_path: Path = DB_PATH):` — использует глобальный DB_PATH как значение по умолчанию. Это нормально, но если DB_PATH изменится, то дефолт останется старым. Лучше использовать None и внутри подставлять. Но не критично.

7. **Строка 36**: `self.db_path.parent.mkdir(parents=True, exist_ok=True)` — создаёт директорию. Ок.

8. **Строка 39**: `self.connection = sqlite3.connect(self.db_path, check_same_thread=False)` — `check_same_thread=False` позволяет использовать соединение из разных потоков, но при этом нужно самостоятельно синхронизировать доступ. Здесь используется `_lock`, так что ок.

9. **Строка 42-43**: `PRAGMA journal_mode=WAL` и `PRAGMA busy_timeout=5000` — выполняются без коммита? На самом деле PRAGMA не требует коммита, но они выполняются в рамках транзакции? В sqlite3 PRAGMA можно выполнять как обычный запрос. Ок.

10. **Строка 45**: `self._initialize()` — вызывается внутри `__init__` без синхронизации? Но `_initialize` декорирован `@_synchronized`, так что он захватит `_lock`. Однако `_lock` уже создан, так что ок.

11. **Строка 47-63**: Создание таблицы events. Всё верно.

12. **Строка 65-75**: Создание таблицы self_proposals. Затем проверка наличия колонки origin и ALTER TABLE. Это нормально, но если таблица уже существует и колонки нет, ALTER добавит. Однако если таблица создана впервые, то колонка origin уже есть в CREATE TABLE, и проверка не нужна. Но код сначала создаёт таблицу с origin, потом проверяет — это избыточно, но не ошибка.

13. **Строка 77-85**: Создание таблицы evidence. Всё верно.

14. **Строка 87-96**: Создание таблицы knowledge. Всё верно.

15. **Строка 98-111**: Создание таблицы personality_history. Всё верно.

16. **Строка 113**: `self.connection.commit()` — коммит после создания таблиц. Ок.

17. **Строка 116-130**: `remember` — вставка события. Всё верно.

18. **Строка 132-151**: `remember_knowledge` — вставка знания. Используется `datetime('now')` для created_at — это время в UTC? В SQLite `datetime('now')` возвращает UTC. Ок.

19. **Строка 153-171**: `get_knowledge` — выборка. Всё верно.

20. **Строка 173-195**: `remember_proposal` — вставка предложения. Используется `datetime.now(timezone.utc).isoformat()` — это строка с временной зоной, например "2025-04-08T12:34:56.789+00:00". В SQLite это сохранится как текст. Ок.

21. **Строка 197-207**: `pending_proposals` — выборка. Ок.

22. **Строка 209-226**: `set_proposal_status` — обновление статуса. Проверка допустимых статусов. Ок.

23. **Строка 228-238**: `recent` — выборка последних событий. Ок.

24. **Строка 240-242**: `close` — закрытие соединения. Ок.

Потенциальные проблемы:

- **Отсутствие обработки ошибок при работе с БД**: если запрос упадёт, исключение пробросится наверх, и программа может упасть. Но это допустимо, так как вызывающий код может обработать.
- **Нет метода для удаления или обновления событий** — не требуется.
- **Нет индексов на часто используемые поля** (например, `owner` в knowledge, `status` в self_proposals). При больших объёмах данных производительность упадёт. MEDIUM.
- **Использование `datetime('now')` в SQLite** — это UTC, но в Python используется `datetime.now(timezone.utc).isoformat()` — тоже UTC. Согласовано.
- **В `remember_proposal` не передаётся `origin` в SQL, если он None?** В коде: `origin` передаётся в execute как параметр, так что если None, то вставится NULL. Ок.
- **В `get_knowledge` нет параметра для сортировки по confidence или фильтрации** — не ошибка.
- **В `_initialize` нет `self.connection.commit()` после ALTER TABLE?** Есть общий commit в конце, так что ок.
- **Потенциальная гонка при создании таблиц**: если два экземпляра Memory создаются одновременно, могут быть конфликты. Но используется блокировка на уровне экземпляра, а не глобальная. Если два потока создадут два экземпляра Memory с одним и тем же файлом, то возможны проблемы. Но в данном приложении, скорее всего, один экземпляр. MEDIUM.
