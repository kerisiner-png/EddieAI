# Локальное ядро решений + LLM как редкий генератор паттернов — дизайн

**Дата:** 2026-08-26 ночь
**Автор:** opencode (главный инженер), решение совета директоров (Эдди)
**Статус:** утверждён, передан на реализацию в свежую сессию

---

## 1. Проблема

Сейчас архитектура зовёт LLM на каждое решение: генерация целей,
планирование, рефлексия, «что делать дальше». Это:
- дорого (каждый тик = вызов облака);
- хрупко (зависит от сети/модели);
- нереалистично (живой ум не «вызывает нейросеть» на каждое действие).

## 2. Принцип (уже в AGENTS.md, но потерян)

> **«Ядро решает — модель только вербализует».**

Живое существо не думает над каждым действием — оно **учится**:
действует по накопленным паттернам, а модель-«учитель» включается
только когда встречает НОВУЮ ситуацию и нужно сформировать новый
паттерн. Это и есть цель Эдди (25-26.08 ночь).

## 3. Архитектура: два слоя

### Слой А — ЛОКАЛЬНОЕ ЯДРО (БЕСПЛАТНО, без модели)

Крутится постоянно 24/7, решает рутину детерминированными правилами,
эвристиками и конечным автоматом состояний:

| Функция | Механизм | Уже есть? |
|---------|----------|-----------|
| Присутствие/цикл жизни | локальный loop | ✅ autonomous_runtime |
| Проверка почты, «прочитать/написать снова» | эвристика (count + время) | ✅ _handle_inbox |
| Выбор активной цели | правила (приоритет×мотивация) | ✅ goal_manager |
| Выбор следующей задачи в плане | правила (порядок/приоритет) | ✅ task_controller |
| Аффективные реакции на события | правила (цель→удовлетворение) | ⚠️ appraisal, нужен локальный |
| **Решение «что делать дальше»** | **конечный автомат + изученные паттерны** | ⚠️ НАДО ПОСТРОИТЬ |
| Маршрутизация действия (research/web/llm/fs) | правила по типу задачи | ✅ action_planner |

### Слой Б — МОДЕЛЬ = редкий «орган обучения/генерации»

Вызывается ТОЛЬКО на настоящую генерацию:

| Момент | Частота |
|--------|---------|
| **Сформировать новый паттерн** в НОВОЙ ситуации (нет совпадения в хранилище) | по факту новизны |
| Создать план для новой цели | 1 раз на цель |
| Выводы дня (консолидация) | 1 раз в сутки |
| Ответить Эдди (новое содержание) | когда он пишет |
| Глубокая саморефлексия | когда сам решит, что есть повод |

## 4. Хранилище паттернов (обучение)

- `evidence` (категория→ценность→уверенность) — уже есть
- `proposal` → lifecycle (CANDIDATE→ACTIVE...) — уже есть
- `HabitPatternDetector`, `ActionPreferenceDetector`,
  `BehaviorPatternDetector` — уже есть, локальные
- **НОВОЕ: ситуация → действие** ключ: кодируем текущее состояние
  (цель, задача, контекст, аффект) → ищем совпадение → если есть,
  действуем локально; если нет — LLM формирует паттерн, сохраняем.

## 5. Ключевой результат

- 5-минутный интервал планировщика УБИРАЕТСЯ: локальное ядро
  крутится постоянно и бесплатно, просто не генерирует без нужды.
- Модель нужна всё реже — паттернов всё больше → бюджет почти
  не расходуется на автономию.
- «Всегда активен 24/7» становится реальностью без костылей.
- LLM = редкие моменты обучения, как у человека.

## 6. Что НЕ делаем

- НЕ добавляем «дневной бюджет-предохранитель» (это костыль).
- НЕ ослабляем/усиливаем интервалы вручную.
- НЕ трогаем мессенджер-общение (оно и так дешёвое/бесплатное).

## 7. Принцип тестирования

- РУТИНА выполняется с НУЛЯ LLM-вызовов (локально).
- LLM вызывается ТОЛЬКО на новизну/генерацию.
- Паттерны накапливаются и переиспользуются между сессиями.
- Бюджет автономии стремится к ~$0/день (модель — редкие события).

## 8. Ограничения

- Детерминированное ядро даёт предсказуемость, но требует аккуратного
  кодирования ситуаций (не переусложнить).
- Первое время много «новых ситуаций» → больше вызовов модели,
  потом резко меньше (кривая обучения).
- Свежая сессия на flash: дизайн уже здесь, контекст чистый → дёшево.
